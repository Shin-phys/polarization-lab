# 仕様書の書き方と改訂ルール

## 1. ファイル

- アプリごとに1フォルダ。`README.md` が入口で、本文は `01-` からの連番とする。
- ファイル名は英小文字とハイフン。本文は日本語。
- 1ファイル1テーマ。長くなったら分割し、`README.md` の索引に追加する。
- 調査結果や候補の一覧など、仕様の本文ではない資料は `reference/` に置く。

## 2. 状態タグ

| タグ | 意味 |
|---|---|
| 【決定】 | 方針として確定したもの |
| 【提案】 | 案として出ているが、まだ確定していないもの |
| 【要検証】 | 実機・実物で確かめないと判断できないもの |

## 3. ID

| 種類 | 形式 | 例 |
|---|---|---|
| 機能要件 | `<アプリ>-F-<番号>` | `WAVE-F-20` |
| 非機能要件 | `<アプリ>-N-<番号>` | `POL-N-02` |
| 未決事項 | `<アプリ>-Q-<番号>` | `POL-Q-01` |

アプリの略号は、WAVE（波の3つの見方）、POL（偏光ラボ）。アプリを追加するときは略号も追加する。

- 番号は機能のまとまりごとに10番台で区切る。
- 削除した要件の番号は欠番とし、再利用しない。

## 4. 未決事項の扱い

1. 未決事項は各アプリの `open-issues` に ID を付けて書く。
2. 決まったら、要件の文書へ反映し、タグを【決定】に変える。
3. `open-issues` の該当項目は削除せず、「解決済み」の節へ移して反映先を書く。
4. `CHANGELOG.md` に1行残す。

## 5. CHANGELOG

- アプリごとに置く。新しいものを上に書く。
- 仕様の版は `0.x`。実装に着手できる状態になったら `1.0` とする。
- 書くのは「何が変わったか」と、関係する ID。

## 6. コミット

- 1つの決定につき1コミット。
- メッセージの先頭にアプリ名を付ける。

```
wave: WAVE-Q-03 を決定（コマ数は T/8 刻み）
pol: 回転台の回転速度を実測して追記（POL-Q-03）
common: iOS の露出制御の検証結果を追記
```

## 7. GitHub Issues（任意）

未決事項を Issue にする場合は、タイトルに ID を入れ、決着したら仕様書へ反映してから閉じる。
仕様書を正とし、Issue は議論の場として使う。
